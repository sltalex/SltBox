# 树能量同步与数据补救

## 已复现的问题

2026-10-26 使用真实 `TreeCloudSyncService` 和可控 API，在本地回归测试复现两条路径：

1. 上一次确认总能量 100、当天增长 80；跨 UTC 日后本地总能量 150、当天增长 5。旧逻辑直接比较不同日期的当天增长，认为本地落后，拉取云端 100 覆盖本地 150。
2. 100 能量的请求已经到达服务端，但响应在网络中丢失；本地随后增长到 150。旧逻辑复用同一操作号，却重新构造 150 的上传量。服务端正常去重后返回 100，客户端把新增的 50 也当作已确认并覆盖。

新增用例在修复前均失败，断言都是 `Expected: 150, Actual: 100`。测试日志保存在本机 `.codex-test-temp/energy-red.log`。

修复后的队列同时持久化完整上传请求、当时本地快照和确认基线。重试原样发送同一请求，只确认那一次提交的增长；重试期间的新增能量继续保留，下一轮以新操作号上传。跨天只比较同一天的日增长，投影确认状态也保留原快照日期，避免把昨天的日增长从今天扣除。

这些测试证明代码存在丢失路径；不能据此断言用户某次历史故障一定由其中一条触发。

## 目前本机证据

修改前已复制进本机 `.codex-test-temp/tree-energy-evidence-20261026-234613/`。这份副本仅用于排查，不提交 Git。当前没有足够证据确定漏记数量，因此没有修改生产账户数值。这是本地确认缓存的检查结果，不等同于本次重新查询生产数据库。

## 补救顺序

1. 先保全证据：停止客户端后复制 `data/tree/progress.json`、`.bak`、整个 `data/sync/tree/`，以及故障前后的账户云备份。保留操作号、日期、确认基线。不要先执行删除同步状态的修复操作，否则会失去计算差额所需的基线。
2. 如果本地数值仍然完整，且同步队列来自修复后的客户端，在“设置 → 功能格子 → 种树”执行同步。未完成的原请求先重传，期间新增的数据在下一轮自动同步（自动周期五分钟）；需要立即确认时再同步一次。核对本地总能量、最后确认状态及云端账户记录。
3. 如果数值已经回落，比较 `progress.json.bak`、`conflict-*.json`、账户云备份中的总能量和日期。再按账户、设备和操作号查询 `tree_progress_operations`，核对已入账的 `energy_delta`、`day_growth_delta`，以及 `tree_profiles`、`tree_daily_progress` 当前值。不同备份通常覆盖同一段增长，不能相加，也不能只取某个较大值覆盖云端。
4. 只有能证明某段增长尚未入账时，才在先备份数据库的前提下补写这一段净差额。必须使用新的唯一补偿操作号并保留审计记录，核对日期、成熟阶段和果实派生规则，避免重复补能量或补发果实。若只剩回落后的相同副本，无法精确推算已经丢失的按键数。

旧版未完成队列只有操作号，没有原请求内容，无法可靠自动重建。新客户端会在继续处理前写出 `conflict-*.json` 本地快照，保留人工核账依据；这不代表已经自动补回历史差额。该兼容措施不能恢复升级前已经被覆盖且没有备份的数据。

## 点击动画

采摘：先完成约 430ms 的放大、发光、淡出动画，再执行树同步和采摘请求。接口确认成功后显示真实到账数量；失败恢复可点击的果实。

动物：先完成约 320ms 的收缩淡出动画，再发送收藏请求。请求结束后刷新背包和状态，失败恢复动物。请求期间防止重复点击，卸载或隐藏界面会取消尚未完成的动画并阻止后续请求。系统关闭动画时保留即时视觉反馈并遵循系统偏好。

本次仅改客户端，不涉及 PHP 协议或数据库迁移，也不发布安装包。
